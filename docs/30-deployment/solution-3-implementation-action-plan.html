Detailed implementation action plan

This runbook is the execution companion to the Solution 3 architecture. It converts the phase estimate into an ordered implementation checklist for the approved baseline: one company-owned Microsoft Entra tenant, one company-owned Azure subscription, six Microsoft 365 Business Premium with Teams licenses, a pooled AVD host pool, and up to 10 Windows access terminals. The implementation owner should maintain the task status, evidence link, issue log, decision owner, and rollback state for every row. Do not place passwords, recovery codes, private keys, or other secrets in the project repository.

AVD changes the operating model from local PCs to centrally hosted Windows sessions. The implementation must therefore validate the user identity, session-host identity, host-pool configuration, golden image, application compatibility, profile storage, access-terminal experience, Azure consumption, and recovery boundaries as one service. Microsoft’s current guidance covers AVD deployment, Entra-joined session hosts, autoscale, FSLogix profiles on Azure Files, and AVD diagnostics. Validate the exact region, image, license entitlement, storage authentication path, and application behavior before production approval.

The task-level ranges below roll up to the architecture document’s 58–104-hour basic implementation estimate; they are hands-on effort estimates, not calendar duration. They assume six initial users, up to 10 access terminals, a simple pooled host pool, one region, supported applications, and no major application redevelopment or regional disaster-recovery design.

Identity + storage owner P2.3, P5.1 2–4 h Authentication and authorization evidence; no AD DS dependency remains in the selected path
P5.3 Configure FSLogix profile settings, naming/quota convention, exclusions, redirection rules, profile cleanup, and pilot assignments; test create, attach, detach, reconnect, concurrent session, and replacement-host behavior. Profile owner P5.2 2–4 h Profile test record and accepted profile settings
P5.4 Configure Azure Files snapshots/backup as approved, independent data backup where required, retention, restore procedure, and fallback profile strategy; restore a profile and prove sign-in to a replacement host. Recovery owner P5.1–P5.3 2–5 h Restore evidence, RPO/RTO result, and documented fallback decision

P6.2 Migrate two representative users with different applications and peripherals; connect from the prepared terminals; validate Entra sign-in, MFA, AVD brokering, profile, Office, Google Workspace, applications, printing, scanning, and communications. Implementer + pilot users P4.5, P5.4, P6.1 2–3 h User/device pilot test results and issue log
P6.3 Test Internet degradation, reconnect, session-host drain/failure, host replacement, profile-storage interruption, application failure, audio/video/peripheral behavior, and support escalation. AVD owner + support owner P6.2 2–3 h Failure-mode results, recovery times, and accepted residual risks
P6.4 Measure user experience and cost at expected concurrency; publish the short user guide and support triage flow; obtain written pilot acceptance and production authorization. Business owner + AVD owner P6.2–P6.3 1–2 h Pilot sign-off, capacity decision, user guide, and production go decision
P7.1 Add production session hosts only after pilot sizing and availability approval; apply the same image, identity, policy, diagnostics, and host-pool settings; verify registration and drain behavior. AVD owner P6.4 1–2 h Production host inventory and health validation
P7.2 Migrate users in small groups; validate each session, profile, application, peripheral, and support path; record user, terminal, host, image, profile, date, acceptance, exception, and rollback status. Implementer + business owner P7.1 1–2 h Completed migration ledger and batch acceptance
P8.1 Observe the service through the approved stabilization period; review AVD health, failed connections, host capacity, scaling, image drift, profile errors, storage, backup, Azure spend, and user-impacting incidents. Support owner P7.2 1–4 h Stabilization log with incidents, resolutions, and accepted risks
P8.2 Run the complete AD DS dependency-removal and controlled domain-controller shutdown test; verify users, terminals, hosts, profiles, applications, DNS/DHCP, printing, certificates, VPN/RADIUS, scripts, and backup continue to work. Implementer + business owner P8.1 0.5–2 h Signed dependency gate and shutdown test result
P8.3 Take the final approved backup and retain the rollback point; demote and retire AD DS only after business-owner approval; revoke unused credentials and remove obsolete dependencies. Implementer + infrastructure owner P8.2 0.5–2 h Demotion record, retained-backup record, and secure retirement checklist
P8.4 Complete handover: update architecture, host/image/application/profile registers, operating and recovery runbooks, support contacts, cost/license register, maintenance calendar, and final acceptance. Project owner + business owner P8.3 0–2 h Handover package and business sign-off

Gate Required decision Minimum evidence If the gate fails
G0 — AVD fit approval AVD solves a documented requirement and the business accepts centralized-session, Internet, profile, support, and consumption trade-offs. Fit decision, capacity baseline, cost ceiling, RTO/RPO, and fallback Stop before production Azure resources; select or redesign the simpler alternative
G1 — Azure foundation ready Tenant, subscription, region, ownership, RBAC, network, quota, budgets, logging, backup boundaries, and recovery contacts are operational. Subscription/resource map, RBAC export, connectivity/quota checks, budget alert, and policy evidence Correct ownership, connectivity, quotas, or governance before AVD deployment
G2 — Identity and image ready AVD authentication, MFA/Conditional Access, licenses, Entra-joined host identity, image applications, licensing, and security controls pass technical tests. License validation, sign-in tests, image version, application matrix, and rollback image Correct identity, licensing, image, or application defects; do not onboard users
G3 — Host-pool and profile ready Workspace, application group, pooled host pool, pilot host, autoscale, diagnostics, Azure Files, Entra Kerberos, and FSLogix pass. Resource/configuration exports, host health, scale test, profile attach, and restore evidence Hold pilot; use the documented profile/storage fallback or redesign
G4 — Pilot acceptance Representative users can work from prepared terminals with acceptable logon, application, profile, peripheral, reconnect, failure, and cost results. Signed pilot test, performance/cost baseline, user guide, and support triage Remediate, resize, change the image/profile, or roll back the pilot
G5 — Production rollout Capacity, availability target, image version, autoscale schedule, support coverage, and migration batches are approved. Production host validation, batch plan, rollback checkpoints, and owner approvals Keep users on the approved fallback and do not expand the pool
G6 — AD DS retirement and handover The service operates without the domain controller and the business can support the AVD environment within budget. Dependency gate, shutdown test, final backup, runbooks, cost/license register, and sign-off Keep AD DS available, extend stabilization, or remediate the dependency

Required implementation evidence

Maintain one controlled evidence register containing the AVD fit and capacity assessment, user/device/application inventory, tenant and Azure subscription ownership record, license eligibility and assignment report, RBAC/network/quota/budget records, identity and authentication tests, image and application register, host-pool configuration, diagnostics and performance baseline, Azure Files/Entra Kerberos/FSLogix permission and restore evidence, terminal readiness checklist, user migration ledger, backup/restore results, change/rollback log, cost and license register, stabilization log, AD DS dependency gate, and final business acceptance. Store sensitive recovery material in the approved password manager or recovery process, not in Markdown, source control, or screenshots.
