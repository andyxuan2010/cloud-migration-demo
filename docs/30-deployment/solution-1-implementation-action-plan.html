Detailed implementation action plan

This runbook is the execution companion to the Solution 1 architecture. It converts the phase estimate into an ordered implementation checklist for the approved baseline: one company-owned Microsoft Entra tenant, one company-owned Azure subscription, six Microsoft 365 Business Premium with Teams licenses, and up to 10 supported Windows 11 Pro PCs. The implementation owner should maintain the task status, evidence link, issue log, and decision owner for every row. Do not place passwords, recovery codes, private keys, or other secrets in the project repository.

The implementation uses Entra join for the Windows sign-in boundary and Intune for device policy, compliance, encryption, application, update, and inventory control. Conditional Access decisions use Entra signals and Intune compliance data; this is why the Business Premium baseline must be active before production enrollment. See the Microsoft Entra joined device guidance, Intune Windows enrollment guide, and Intune Conditional Access guidance.

The task-level ranges below roll up to the architecture document’s 36–54-hour baseline implementation estimate; they are hands-on effort estimates, not calendar duration. They assume a clean six-user implementation with simple Windows profiles, supported applications, and no major AD-hosted dependency remediation.

Implementer P4.1 2–3 h Pilot device is Entra joined, Intune managed, encrypted, compliant, and usable
P4.3 Run pilot acceptance: Windows sign-in, MFA, Office, Google Workspace, applications, printing, scanning, communications, updates, recovery, and support escalation. P5.1 Create the production batch schedule, user communications, per-device rollback checkpoints, support coverage, maintenance window, and migration ledger. Project owner P4.3 1–1 h Approved batch plan and user/device sequence
P5.2 Migrate one or two PCs per batch: back up, migrate/rebuild profile, Entra join, Intune-enroll, apply policies, restore data, validate applications, and record exceptions. Implementer P5.1 2–3 h Each device has a completed migration record and a named acceptance result
P5.3 Obtain user acceptance for each batch; confirm compliance, BitLocker escrow, LAPS, application/peripheral operation, Google SSO, and support readiness before continuing. User representative + implementer P5.2 1–2 h Batch sign-off; failed devices remain on the rollback path
P6.1 Move DHCP and DNS forwarding to the router/firewall or approved managed service; test reservations, name resolution, time synchronization, and Internet/service reachability. Network owner P5.3 1–2 h Network change record and tests from every production segment
P6.2 Migrate or retire file shares, mapped drives, print queues, certificates, VPN/RADIUS, scripts, scheduled tasks, service accounts, backup agents, and management dependencies. Implementer + application owners P0.2, P5.3 1–2 h Dependency register shows a replacement, retirement, or approved waiver for every item
P6.3 Run the full dependency-removal test from production PCs, including offline/reconnect behavior, printers, scanners, business applications, backup, restore, and administrator recovery. Implementer + business owner P6.1–P6.2 1–1 h AD DS retirement gate is fully evidenced; no critical dependency remains
P7.1 Observe the migrated environment through the approved stabilization period; review identity, device, security, backup, network, application, cost, and Azure subscription alerts. Support owner P5.3–P6.3 0.5–1.5 h Stabilization log with incidents, resolutions, and accepted residual risks
P7.2 Perform a controlled domain-controller shutdown test during the approved rollback window; verify that users, applications, DNS/DHCP, backup, and support procedures continue to work. Implementer + business owner P6.3, P7.1 0.25–1.5 h Shutdown test passes or rollback is executed and documented
P7.3 Demote and retire AD DS only after the gate passes; retain the approved backup, remove obsolete dependencies, revoke unused accounts, update diagrams/runbooks, and obtain final acceptance. Implementer + business owner P7.2 0.25–1 h Demotion record, retained-backup record, final documentation, and sign-off

Go/no-go gates

Gate Required decision Minimum evidence If the gate fails
G0 — Design approval Scope, baseline licenses, tenant/subscription ownership, RPO/RTO, rollback, and acceptance tests are approved. Signed decision record and implementation window Remain in discovery; do not create production policies or migrate devices
G1 — Foundation ready Tenant, domain, Business Premium licenses, admins, recovery, Azure RBAC, budgets, alerts, and governance are operational. Tenant/subscription register, license report, RBAC export, alert test Correct ownership, licensing, or governance before enrollment
G2 — Pilot ready Intune baseline, Entra join, MFA/Conditional Access, encryption, LAPS, updates, apps, and Google SAML pass technical tests. Pilot device evidence and authentication test record Correct policies or application packaging; keep production PCs unchanged
G3 — Production migration Pilot user accepts the experience and rollback has been tested. Pilot sign-off and approved batch schedule Roll back the pilot or hold the next batch
G4 — AD DS retirement All dependency-removal, network, backup/restore, user, application, and support tests pass. Completed dependency register and shutdown test Keep AD DS available; remediate or formally waive the dependency
G5 — Handover The environment is stable, recurring cost is within budget, and the business can operate the service. Runbooks, registers, diagrams, support contacts, and sign-off Extend stabilization and close documentation gaps

Required implementation evidence

Maintain one controlled evidence register containing the discovery/dependency inventory, user and device migration ledger, tenant and Azure subscription ownership record, license assignment report, RBAC and emergency-access record, policy/configuration register, authentication and device test results, backup/restore evidence, change/rollback log, cost and license register, incident/stabilization log, and final business acceptance. Store sensitive recovery material in the approved password manager or recovery process, not in Markdown, source control, or screenshots.
