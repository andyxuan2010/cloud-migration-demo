# Solution 3 — Azure Virtual Desktop

## Detailed implementation action plan

This runbook is the execution companion to the [Solution 3 architecture](azure_virtual_desktop_architecture.md). It converts the phase estimate into an ordered implementation checklist for the approved baseline: one company-owned Microsoft Entra tenant, one company-owned Azure subscription, six Microsoft 365 Business Premium with Teams licenses, a pooled AVD host pool, and up to 10 Windows access terminals. The implementation owner should maintain the task status, evidence link, issue log, decision owner, and rollback state for every row. Do not place passwords, recovery codes, private keys, or other secrets in the project repository.

AVD changes the operating model from local PCs to centrally hosted Windows sessions. The implementation must therefore validate the user identity, session-host identity, host-pool configuration, golden image, application compatibility, profile storage, access-terminal experience, Azure consumption, and recovery boundaries as one service. Microsoft’s current guidance covers [AVD deployment](https://learn.microsoft.com/en-us/azure/virtual-desktop/deploy-azure-virtual-desktop), [Entra-joined session hosts](https://learn.microsoft.com/en-us/azure/virtual-desktop/azure-ad-joined-session-hosts), [autoscale](https://learn.microsoft.com/en-us/azure/virtual-desktop/autoscale-scaling-plan), [FSLogix profiles on Azure Files](https://learn.microsoft.com/en-us/azure/virtual-desktop/store-fslogix-profile), and [AVD diagnostics](https://learn.microsoft.com/en-us/azure/virtual-desktop/diagnostics-log-analytics). Validate the exact region, image, license entitlement, storage authentication path, and application behavior before production approval.

The task-level ranges below roll up to the architecture document’s **58–104-hour** basic implementation estimate; they are hands-on effort estimates, not calendar duration. They assume six initial users, up to 10 access terminals, a simple pooled host pool, one region, supported applications, and no major application redevelopment or regional disaster-recovery design.

### Go/no-go gates

| Gate | Required decision | Minimum evidence | If the gate fails |
|---|---|---|---|
| **G0 — AVD fit approval** | AVD solves a documented requirement and the business accepts centralized-session, Internet, profile, support, and consumption trade-offs. | Fit decision, capacity baseline, cost ceiling, RTO/RPO, and fallback | Stop before production Azure resources; select or redesign the simpler alternative |
| **G1 — Azure foundation ready** | Tenant, subscription, region, ownership, RBAC, network, quota, budgets, logging, backup boundaries, and recovery contacts are operational. | Subscription/resource map, RBAC export, connectivity/quota checks, budget alert, and policy evidence | Correct ownership, connectivity, quotas, or governance before AVD deployment |
| **G2 — Identity and image ready** | AVD authentication, MFA/Conditional Access, licenses, Entra-joined host identity, image applications, licensing, and security controls pass technical tests. | License validation, sign-in tests, image version, application matrix, and rollback image | Correct identity, licensing, image, or application defects; do not onboard users |
| **G3 — Host-pool and profile ready** | Workspace, application group, pooled host pool, pilot host, autoscale, diagnostics, Azure Files, Entra Kerberos, and FSLogix pass. | Resource/configuration exports, host health, scale test, profile attach, and restore evidence | Hold pilot; use the documented profile/storage fallback or redesign |
| **G4 — Pilot acceptance** | Representative users can work from prepared terminals with acceptable logon, application, profile, peripheral, reconnect, failure, and cost results. | Signed pilot test, performance/cost baseline, user guide, and support triage | Remediate, resize, change the image/profile, or roll back the pilot |
| **G5 — Production rollout** | Capacity, availability target, image version, autoscale schedule, support coverage, and migration batches are approved. | Production host validation, batch plan, rollback checkpoints, and owner approvals | Keep users on the approved fallback and do not expand the pool |
| **G6 — AD DS retirement and handover** | The service operates without the domain controller and the business can support the AVD environment within budget. | Dependency gate, shutdown test, final backup, runbooks, cost/license register, and sign-off | Keep AD DS available, extend stabilization, or remediate the dependency |

### Required implementation evidence

Maintain one controlled evidence register containing the AVD fit and capacity assessment, user/device/application inventory, tenant and Azure subscription ownership record, license eligibility and assignment report, RBAC/network/quota/budget records, identity and authentication tests, image and application register, host-pool configuration, diagnostics and performance baseline, Azure Files/Entra Kerberos/FSLogix permission and restore evidence, terminal readiness checklist, user migration ledger, backup/restore results, change/rollback log, cost and license register, stabilization log, AD DS dependency gate, and final business acceptance. Store sensitive recovery material in the approved password manager or recovery process, not in Markdown, source control, or screenshots.
