# Solution 1 — Microsoft Entra ID + Intune

## Detailed implementation action plan

This runbook is the execution companion to the [Solution 1 architecture](entra_id_intune_architecture.md). It converts the phase estimate into an ordered implementation checklist for the approved baseline: one company-owned Microsoft Entra tenant, one company-owned Azure subscription, six Microsoft 365 Business Premium with Teams licenses, and up to 10 supported Windows 11 Pro PCs. The implementation owner should maintain the task status, evidence link, issue log, and decision owner for every row. Do not place passwords, recovery codes, private keys, or other secrets in the project repository.

The implementation uses Entra join for the Windows sign-in boundary and Intune for device policy, compliance, encryption, application, update, and inventory control. Conditional Access decisions use Entra signals and Intune compliance data; this is why the Business Premium baseline must be active before production enrollment. See the [Microsoft Entra joined device guidance](https://learn.microsoft.com/en-us/entra/identity/devices/concept-directory-join), [Intune Windows enrollment guide](https://learn.microsoft.com/en-us/intune/device-enrollment/windows/guide), and [Intune Conditional Access guidance](https://learn.microsoft.com/en-us/intune/device-security/conditional-access-integration/overview).

The task-level ranges below roll up to the architecture document’s **36–54-hour** baseline implementation estimate; they are hands-on effort estimates, not calendar duration. They assume a clean six-user implementation with simple Windows profiles, supported applications, and no major AD-hosted dependency remediation.

### Go/no-go gates

| Gate | Required decision | Minimum evidence | If the gate fails |
|---|---|---|---|
| **G0 — Design approval** | Scope, baseline licenses, tenant/subscription ownership, RPO/RTO, rollback, and acceptance tests are approved. | Signed decision record and implementation window | Remain in discovery; do not create production policies or migrate devices |
| **G1 — Foundation ready** | Tenant, domain, Business Premium licenses, admins, recovery, Azure RBAC, budgets, alerts, and governance are operational. | Tenant/subscription register, license report, RBAC export, alert test | Correct ownership, licensing, or governance before enrollment |
| **G2 — Pilot ready** | Intune baseline, Entra join, MFA/Conditional Access, encryption, LAPS, updates, apps, and Google SAML pass technical tests. | Pilot device evidence and authentication test record | Correct policies or application packaging; keep production PCs unchanged |
| **G3 — Production migration** | Pilot user accepts the experience and rollback has been tested. | Pilot sign-off and approved batch schedule | Roll back the pilot or hold the next batch |
| **G4 — AD DS retirement** | All dependency-removal, network, backup/restore, user, application, and support tests pass. | Completed dependency register and shutdown test | Keep AD DS available; remediate or formally waive the dependency |
| **G5 — Handover** | The environment is stable, recurring cost is within budget, and the business can operate the service. | Runbooks, registers, diagrams, support contacts, and sign-off | Extend stabilization and close documentation gaps |

### Required implementation evidence

Maintain one controlled evidence register containing the discovery/dependency inventory, user and device migration ledger, tenant and Azure subscription ownership record, license assignment report, RBAC and emergency-access record, policy/configuration register, authentication and device test results, backup/restore evidence, change/rollback log, cost and license register, incident/stabilization log, and final business acceptance. Store sensitive recovery material in the approved password manager or recovery process, not in Markdown, source control, or screenshots.
